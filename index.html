Effect of expert parallelism (current model, GPU, X × Y, w)

Changing EP only changes the FSDP gather term. Model states stay at 1/N, and the token-dispatch buffers stay at about tokens × top-k × Hmoe × 2 B. Higher EP does raise routing imbalance (see notes).

Breakdown

The formula

tokens per GPU T = S × MBS / Y model states = (4 + b_opt) × P / N b_opt = 12 (Adam) or 8 (Muon); N = X × Y layer checkpoints = L × 2 B × H × T full activation checkpointing: one bf16 input per layer transient = w × T × H × 2 B one layer's recompute + MoE dispatch + attention + backward logits = n_logit × T × V × 4 B 0 at peak with the chunked log-prob path FSDP gather = c × 2 B × [ (P − E) / L + E / (L × EP) ] c live copies of one layer's local bf16 params allocated peak = states + checkpoints + transient + logits + gather reserved peak = allocated × (1 + frag) fits if reserved peak ≤ GPU capacity − non-PyTorch reserve

Only model states shrink as you add FSDP GPUs. Checkpoints, transient memory and logits depend only on tokens per GPU (S / Y), so CP/SP is the lever for them. The gather buffers depend on EP. With FSDP alone you eventually hit a floor where the per-token terms fill the GPU, and adding FSDP GPUs no longer helps.

What the persistent state looks like (measured)

The 12 B/param for Muon is fp32 parameter shard (4) + fp32 gradient shard (4) + fp32 momentum (4). There is no persistent bf16 weight copy: FSDP2 casts to bf16 only while gathering a layer. Adam adds a second moment: 4 + 4 + 4 + 4 = 16 B. This matches the "4 B weights+grads + 12/8 B optimizer" accounting in total, though the split differs.

How the FSDP gather term is estimated, and how EP changes memory

FSDP keeps each GPU's parameters as a 1/N shard. To run a layer, it all-gathers that layer's parameters into a bf16 flat buffer, copies them out into unsharded tensors, then frees them (reshard after forward). In backward it also holds that layer's unsharded bf16 gradient as the reduce-scatter input. At any moment about c ≈ 2 copies of one layer are live; the snapshot measured 1.9.

With EP, a GPU only gathers its own experts. Each GPU holds 1/EP of each layer's routed experts, and FSDP shards those across the other N/EP GPUs. Non-expert weights (attention, norms, router, shared experts) are not divided by EP. So one layer's local bf16 size is 2 B × [(P − E)/L + E/(L·EP)].

  • Model states: unchanged by EP. Experts are still sharded 1/N overall; the snapshot's 43.2 GiB param shard equals exactly 4 B × 744B / 64.
  • FSDP gather: the expert part falls as 1/EP. For GLM-5.2: EP 1 → 36.9 GiB, EP 2 → 18.9, EP 4 → 9.9, EP 8 → 5.4, EP 16 → 3.2, EP 64 → 1.5. The non-expert part (~0.5 GiB/layer) is a floor, so beyond EP 8 the savings are only a few GiB.
  • Token-dispatch buffers: each is about T × top-k × Hmoe × 2 B, independent of EP. The snapshot shows 2.09 GiB buffers = 22.8K × 8 × 6144 × 2 B, with about six live at once (~14 GiB). These are included in w.
  • Routing imbalance: receive buffers depend on how many tokens hit this GPU's experts. The snapshot's largest receive buffer was 2.47 GiB against the 2.09 average (1.18×) at EP 8 with 32 experts per GPU. Fewer experts per GPU (higher EP) average out less, so the worst rank's peak can grow.
  • Layout: EP must divide N and the expert count. It usually stays within NVLink (≤ 8 per node, or one NVL72 domain), because all-to-all across nodes is slow.

Kimi K3 / K3.1 preset

From the Hugging Face config.json: 93 layers (1 dense), H = 7168, 896 routed experts (top-16) + 2 shared, expert FFN 3072 on a 3584-dim latent (latent MoE), vocab 163,840. The model card says 2.8T total / 104B active. Routed experts are 92 × 896 × 3 × 3584 × 3072 ≈ 2.72T, and the computed total is ≈ 2.78T. Dispatch per token is 16 × 3584 = 8 × H, the same multiple of H as GLM (8 × 6144), so the GLM-calibrated w is a reasonable first guess. Its attention (69 KDA linear-attention + 24 DSA/MLA layers) differs from GLM's, so recalibrate w from a Kimi snapshot before relying on it.

Caveats

  • The per-token terms come from one model family (GLM MoE + sparse attention, one MoE kernel implementation, EP 8). Dense models or other attention kernels will have a different w, so recalibrate from a snapshot.
  • Linear scaling in tokens per GPU is assumed. The MoE routing buffers depend on routing balance, and the worst rank sets the peak.
  • Throughput, global-batch divisibility (the number of DP replicas X must divide the packed batch count), and the cost of SP all-to-all are not modeled. Memory is necessary, not sufficient.
